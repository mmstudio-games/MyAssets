> 面向**开发者/贡献者**：记录产品设计的技术决策与依据，避免重复讨论、防止遗忘"为什么这么做"。
> 来源：早期技术方案讨论沉淀（原"技术方案与交接文档"），已按主题归入本文件与 architecture.md。

## 1. 核心构想：为什么"HTML → 引擎资产"成立

- **效果 = 资产，不是运行时计算**：渐变/光晕/辉光在游戏行业是美术画好的 PNG 贴图，引擎只负责摆放；CSS 里"引擎现算"的效果，游戏里都是资源。
- **Shader/后处理只用于动态程序化效果**（Bloom/扭曲/流光），由技术美术（TA）编写。
- **静态界面预渲染是行业标准**：标题屏/结算屏整屏出图，引擎只铺图。
- **本产品颠覆点**：把"AI 不擅长写的引擎 shader/粒子参数"换成"AI 极其擅长写的 HTML/CSS"——浏览器渲染内核出图（像素级 = 浏览器渲染结果），作为资产给引擎播放。

## 2. 出图原理：CDP 内核接口出图

- `page.screenshot()` 走 CDP `Page.captureScreenshot`，**直接从渲染内核的合成帧缓冲读回该帧**，与屏幕所见逐像素一致——不是截图工具，无二次处理。
- 更底层等价物：`--headless --screenshot`、`canvas.toDataURL()`，效果无差别，抓的是同一帧。
- **精度差异来自抓帧时机，而非抓取方式**：字体就绪、动画定位、DPR、尺寸裁剪。
- **导出不触发合并重绘**：CDP captureScreenshot 只是读缓冲，无副作用。

## 3. "每帧信号量"讨论结论（多通道汇聚）

- **纯 DOM/CSS 动画**：不存在"逐元素渲染完成信号"——同一帧管线（style→layout→paint→composite→提交缓冲）统一推进，所有动画同帧完成；**双 rAF 门控就是最强的"管线完成信号"**。
- **跨渲染通道**（canvas 2D / WebGL / iframe / 视频 / 图片 / 字体）：各通道提交时机独立，**必须逐通道等待再汇聚**：

```js
await Promise.all([document.fonts.ready, ...imgs.map(i => i.decode())]); // 资源层
await new Promise(res => requestAnimationFrame(() => requestAnimationFrame(res))); // 管线层
await Promise.all([iframeReady, canvasCommit]); // 独立通道
```

- 当前 render.js 覆盖"纯 DOM/CSS + 图片 + 字体"场景；跨通道汇聚规则（3.3 节）为后续支持 canvas/WebGL 场景预留。

## 4. AI 生成网页的迭代性问题（"首版最好"）

真实存在，根因可解：
- 根因：上下文漂移、CSS 全局耦合（flex/z-index/继承）、盲改（改代码不看渲染结果）。
- 解法：**组件化/设计系统**（改局部不波及其他）、**视觉回归自动化**（改后自动截图 diff）、**重生成优于修补**（布局级改动让 AI 重写场景，首版质量最高）、**参数化**（间距/颜色/字号外置成 theme 变量）。
- **对本品是顺风**：游戏素材是一次性资产，重新生成成本远低于修旧布局，天然绕开迭代难题。

## 5. 验证架构（AI 能否验证自己写的网页）

| 层次 | 可靠性 | 说明 |
|---|---|---|
| 程序化断言 | ⭐⭐⭐⭐⭐ 确定性 | AI 写断言脚本：元素不重叠/不溢出/尺寸对/字体就绪 |
| Golden-image diff | ⭐⭐⭐⭐⭐ 确定性 | 基线 vs 当前逐像素对比（视觉回归测试，行业标准） |

结论：验证应做成确定性管道（断言 + diff），不靠 AI 看图。
当前状态：程序化断言已实现（test/ 全链路）；golden-image diff 已实现（`myassets golden`）。

## 6. 市场空白与差异化

### 参照产品调研（"HTML/CSS → 视频/图片"方向最接近的产品）

- **定位**：面向视频创作者的"React 组件 → 程序化视频"渲染工具（TypeScript，日更维护，社区活跃）。
- **能力边界**（源码级验证，90 个渲染选项实证）：输出止步于"图片 + 视频 + 序列帧"，**整个 renderer 无任何 sprite sheet / 图集 / 九宫格 / 纹理压缩 / 引擎导入**，`sprite` 一词零出现 → 游戏资产层 0 覆盖。
- **对我们的启示**：该方向工具把"HTML/CSS → 图片/视频"做得很深，但**游戏引擎资产层是空白**——这正是本品的切入点（见下方差异化表）。

### 市场空白（GitHub 仓库搜索实证）

| 查询 | 结果 |
|---|---|
| `html css sprite sheet generator` | 仅 2 个（★4/★0），均为"上传图片拼精灵图"，非 HTML 渲染 |
| `playwright sprite sheet` | **0 结果** |
| `browser render game assets` | 6 个，全不相关 |

→ **"HTML/CSS 渲染 → 游戏引擎资产"细分确认空白。**

### 差异化表（参照产品不做、我们必须做的）

| 能力域 | 参照产品现状 | 我们的缺口（= 产品核心） |
|---|---|---|
| 游戏引擎资产导出 | 输出 MP4/WebM/PNG 序列帧即止 | 精灵图打包、纹理图集、九宫格切图、ASTC/ETC/KTX2 压缩、引擎 `.meta`/`.plist`/`.import` 生成 |
| 可伸缩 UI 资产 | 只有"整帧图像"概念 | 按钮/面板/进度条的九宫格切片 + 边框测量自动化 |
| HTML/CSS 原生资产源 | 必须写 React 组件树 | "独立 .html 文件即场景"的一等公民抽象 |
| 游戏引擎运行时 | Player 只在浏览器播 | Cocos/Godot/UE5 帧装配器、透明 WebM 播放器、精灵图组件 |
| 场景编排配置 | 无资产需求描述 | `scene.yaml` 式配置 |
| 游戏化约束 | 视频无需无缝循环 | 无缝循环检测、静态层+动画层分层导出、包体预算管理 |
| AI 工作流 | prompt-to-视频 | prompt-to-游戏资产 |

**护城河判断**：必须建在"游戏引擎导入器 + 资产格式 + 引擎帧装配"上——这是视频工具方向不会碰的深水区。

## 7. 技术风险与注意事项

1. **包体/内存**：24 帧全屏 430×932@2x PNG ≈ 70MB+。解法：WebP（带透明）、图集、小尺寸+引擎放大、背景静态+局部动画、或 WebM 透明视频。
2. **字体版权**：浏览器系统字体导出的商用授权问题 → 用有授权的 Web 字体（woff2 内嵌）或购买字库。
3. **交互 UI 不能预渲染**：按钮/列表/滚动留给引擎实时；预渲染只做"静态层 + 装饰动画"。
4. **跨端一致**：锁定 Chrome 版本渲染，导出后各平台位图一致（这是优势）。
5. **编码/许可**：MIT 协议（见 `LICENSE`）；全自研，不引入任何第三方渲染产品代码。

## 8. Roadmap（未完成项）

### MVP 定义（最小可行闭环，原方案第六节）

```
CLI：myassets（产品名 MyAssets，仓库目录 myassets/）
> 2026-08-29 改定：包名 / 命令由 `my-assets` 改为 `myassets`——与产品名 MyAssets 小写完全一致、用户打字更简（少一个连字符），且两名字在 npm 均未被占用。
├─ scenes/*.html          # AI 生成的界面/特效（HTML+CSS+WAAPI）
├─ scene.yaml             # 资产配置：尺寸/DPR/帧率/帧数/输出格式/九宫格声明
├─ render                 # 确定性逐帧渲染 → PNG/WebP 序列帧 / 精灵图 / WebM
├─ pack                   # 精灵图打包 + 九宫格自动切图 + 图集生成
└─ import                 # → Cocos Creator / Unity 资源目录（.plist/.meta/图集）
```

验证闭环（两层）：

```
AI 写 HTML → 渲染出图
  → ① 程序化断言（无重叠/无溢出/尺寸对）     确定性
  → ② 像素 diff（vs 基线/目标）              确定性
  → 反馈给 AI → 重生成或局部修 → 再验证
```

落地顺序：原型验证最痛点（一个 HTML 场景含动画 → 确定性逐帧渲染 → PNG 序列帧 → 九宫格自动切图 → 输出 Cocos 可导入目录，跑通全链路）→ scene.yaml 配置化 + 程序化断言 → golden-image diff → 再评估 Cocos/Unity 导入器插件与引擎侧运行时组件。
